# Data Inspection Report

Per-file inspection of all 14 raw CU-BEMS CSVs (7 floors x 2 years), before any resampling or merging. Generated by `src/inspect_data.py`.

## Key findings

- **2018 nominal coverage**: 2018-07-01 00:00:00 to 2018-12-31 23:59:00.
- **2019 nominal coverage**: 2019-01-01 00:00:00 to 2019-12-31 23:59:00.
  -> 2018 files only cover **Jul 1 - Dec 31** (184 days), not a full year; 2019 files cover the full calendar year. The 2018 train set is therefore H2-only and has no H1 seasonal coverage -- keep this in mind when interpreting train/test results, since the model never sees H1 2018 patterns during training.

- **2019Floor6.csv is truncated mid-year**: last timestamp is 2019-10-22 13:27:00 (expected 2019-12-31 23:59:00), with a malformed final line in the raw file. Floor 6 has **no 2019 data from 2019-10-22 to year end** (~70 days missing entirely) -- this floor will have fewer test rows in Q4 2019 than the others.

- **No missing timestamp rows**: every file has a complete minute-level timestamp index (gaps >5min between consecutive readings = 0 everywhere, aside from the truncation above). Missing data instead shows up as **NaN cells within existing rows** -- sensors going blank while the logger keeps ticking, not the logger stopping.
- **kW missingness is highly variable**: mostly <1% for most columns/floors, but spikes as high as ~25% for specific zones in specific files (e.g. Floor 3 2018 z1_AC1-3 at 25.3%, Floor 4 2019 z1_AC1-3 at 25.5%) -- consistent with documented CU-BEMS sensor/circuit dropout episodes rather than uniform random noise.
- **Sensor (temp/RH/lux) columns are missing much more often** than kW columns -- commonly 18-73% missing in 2018 files, and some zones are **100% missing** (column exists, sensor was never installed/active there, e.g. Floor 2 2018 zone 4). Sensor features will need per-floor/zone availability checks before use.
- **No negative kW readings** in any file (0 negative cells across all 14 files) -- consumption meters behave as expected, no sign-flip cleanup needed.
- **Extreme spikes exist** (readings >5x a column's 99th percentile), concentrated in a few AC columns/files rather than spread evenly -- e.g. 2018Floor6 z4_AC2/AC3 (~1500-1600 flagged rows each), 2019Floor3 z1_AC2 (1782), 2019Floor4 z1_AC2 (1525), 2019Floor6 z4_AC2 (2468). These look like sensor-fault spikes (stuck-high readings) rather than genuine demand peaks, and will need explicit outlier handling in the cleaning step.
